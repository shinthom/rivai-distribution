**1. CORS의 본질 — 서버가 허락하는 메커니즘**

1/ CORS(교차 출처 자원 공유)는 브라우저가 구현한 '보안 장치'다. 브라우저는 기본적으로 자신이 접속한 도메인(예: 홈페이지)과 다른 도메인(예: R2 스토리지)으로 HTTP 요청을 보낼 때, 상대방 서버가 허락했는지 반드시 확인한다.

2/ 핵심은 CORS가 클라이언트(브라우저) 단에서 임의로 끄거나 우회할 수 있는 기술이 아니라는 점이다. 요청을 받는 서버(Cloudflare R2) 측에서 헤더(`Access-Control-Allow-Origin`)를 통해 "이 홈페이지 도메인은 내 데이터를 읽어가도 좋다"고 명시적으로 허락해 주어야만 브라우저가 차단을 해제한다.

3/ 간혹 개발 중 CORS 에러를 만나면 런처 코드나 웹 프론트엔드 코드를 수정하려 드는 실수를 한다. 하지만 해결책은 언제나 데이터를 서빙하는 '서버 설정'에 있다. R2 버킷의 CORS Policy에 홈페이지 도메인을 허용 타겟으로 등록하는 것이 유일하고 올바른 정공법이다.

**2. Cache-Control 분리 전략 — 메타데이터와 자산의 캐시 차별화**

1/ 대용량 배포 인프라에서 CDN 캐시(Cache) 설정은 비용과 직결된다. 하지만 모든 파일에 같은 캐시 규칙을 적용하면 대형 장애가 발생한다. 매번 변하는 메타데이터인 `manifest.json`과 데이터가 고정된 빌드 `zip` 파일의 캐시 전략을 철저히 분리해야 한다.

2/ `manifest.json`은 버전이 바뀌자마자 유저가 즉시 알아채야 하므로 캐시 기간을 없거나 매우 짧게 잡아야 한다(`max-age=0` 또는 `no-cache`). 캐시를 길게 잡으면 서버에 새 빌드를 올렸는데도 유저 런처가 옛날 manifest 캐시를 읽어 업데이트를 감지하지 못하는 지옥이 펼쳐진다.

3/ 반면 빌드 `zip` 파일은 한 번 올라가면 내용이 절대 바뀌지 않는 불변(Immutable) 자산이다. 따라서 캐시 기간을 몇 달 이상으로 길게 설정해야 한다(`max-age=31536000`). 그래야 전 세계 유저가 몰려도 R2 원본 서버로 요청이 가지 않고 집 근처 CDN에서 초고속으로 다운로드되어 서버 부하와 비용을 극적으로 아낄 수 있다.

**3. 정적 사이트의 동적성 패턴 — SSR 없이 최신 데이터 보여주기**

1/ 서버가 실시간으로 HTML을 그려서 내려주는 SSR(서버 사이드 렌더링) 없이, Cloudflare Pages 같은 단순 정적(Static) 호스팅만으로도 홈페이지에 실시간 최신 버전과 패치노트를 띄울 수 있다. 배포 파이프라인과 클라이언트 렌더링을 조합하는 패턴 덕분이다.

2/ 홈페이지(HTML/JS) 자체는 완전히 고정된 정적 파일로 빌드되어 전 세계 CDN에 뿌려진다. 유저가 홈페이지에 접속하는 순간, 정적 HTML에 포함된 자바스크립트가 브라우저 환경에서 `fetch()`를 통해 R2에 있는 `manifest.json`을 비동기적으로 긁어온다.

3/ 브라우저가 읽어온 최신 JSON 데이터(`latestVersion`, `patchNotesUrl` 등)를 기반으로 화면의 텍스트와 다운로드 링크를 실시간으로 갈아끼운다. 이 패턴을 쓰면 값싸고 트래픽에 무적 인 정적 호스팅을 유지하면서도, 빌드 배포 시 `manifest.json` 하나만 교체하는 것으로 홈페이지 전체를 동적으로 제어할 수 있다.
