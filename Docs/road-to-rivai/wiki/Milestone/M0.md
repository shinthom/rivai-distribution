# M0: Test Distribution Pipeline

## 목표

팀원이 홈페이지에서 런처를 받아 최신 빌드를 설치·실행하고, 테스트 서버에 접속해 피드백·로그를 제출할 수 있게 한다. M0는 게임 콘텐츠가 아니라 M1~M5를 반복 테스트 가능하게 만드는 시스템이다.

## 완료 한 줄

> 팀원이 새 PC에서 홈페이지 ➔ 런처 ➔ 설치 ➔ Play ➔ 테스트 서버 접속 ➔ Build Version 확인 ➔ 피드백·로그 제출까지 수행할 수 있다.

## 포함 범위

| 항목 | 목적 |
|---|---|
| 홈페이지 v0 | 다운로드·패치노트·가이드·피드백 링크 |
| 런처 v0 | 최신 빌드 다운로드·업데이트·실행 |
| `manifest.json` | 버전·URL·sha256·서버 주소 관리 |
| 빌드 저장소 | 클라/서버 zip 보관 |
| 테스트 서버 | 고정 접속 서버 1개 |
| 피드백 폼 | 버그·조작감·네트워크 수집 |
| 로그 수집 | Logs 폴더 열기, Build Info 복사 |
| 패치노트 | 빌드별 변경 사항 |
| 빌드 자동화 초안 | 반복 가능한 BuildCookRun |

## 제외 범위

| 제외 | 이유 |
|---|---|
| 회원가입/로그인 | 배포 우선 |
| 결제·랭킹·매치메이킹 | 프로토타입 비핵심 |
| 차등 패치 | 초반엔 전체 zip이면 충분 |
| 상용 안티치트 | M5 이후 별도 마일스톤 |
| 화려한 홈페이지 | 테스터 포털 역할이면 충분 |

## 초기 결정

| 항목 | 결정 |
|---|---|
| 플랫폼 | Windows, Mac |
| 인증 | 로그인 없음 (필요 시 공유 비밀번호) |
| 배포 | 전체 zip 다운로드 |
| 업데이트 | `Version.txt` vs `manifest.latestVersion` 비교 |
| 서버 | 고정 1개. M0.1은 Listen 허용, M0.3부터 Dedicated |
| 피드백 | Google Form / Notion / Discord 중 택1 |
| 로그 제출 | Logs 폴더 열기 |
| 런처 | C# WPF 또는 WinUI |
| 홈페이지 | 정적 사이트 |
| 빌드 | 수동 → BuildCookRun 스크립트화 |

## 흐름

```text
Dev ➔ Client/Server Build ➔ 압축 ➔ Storage 업로드 ➔ manifest.json 갱신
   ➔ Homepage/Launcher 인식 ➔ Tester 다운로드·실행
   ➔ Test Server 접속 ➔ Feedback·Log 제출
```

## 추가로 살펴봐야 할 것

대부분 "M0 다음 사이클" 또는 "Windows 라인 보강" 범주다. M0 완료 한 줄을 깨는 정도는 아니지만, M1 진입 전에 한 번씩 짚고 가는 게 좋다.

### 1) Windows 클라이언트 빌드 라인 — 가장 큰 빈칸
- 현재 manifest `dev.json` 에 `client.win64` 자체가 없다 → portal에서 "Coming soon"으로 disabled.
- macOS 만 cooking·archive 검증된 상태. Windows 호스트(혹은 CI Windows runner) 에서 `RunUAT BuildCookRun -platform=Win64` 한 번 통과시키고 `release-game.sh --client-win64 …` 로 묶을 것.
- Windows SmartScreen 우회(EV 코드 사인 또는 안내 문서) 도 함께 결정 필요. J01 의 macOS 모델을 윈도우에 평행 이식.

### 2) Windows 런처 publish 누락
- `launcher-release.yml` 은 Windows job 까지 실행되도록 짜여 있지만, `Distribution/manifest/launcher/dev.json` 로컬 스냅샷은 여전히 0.0.1 + mac 만 있다.
- 실제 R2 manifest 가 win64 entry 를 가지고 있는지 확인 후, portal 런처 카드(Windows) 가 활성화되는지 검증.

### 3) 게임 내 Build Version HUD

### 4) `install-guide/` 페이지 부재
- C01 에서 합의한 `Distribution/portal/install-guide/index.html` 이 아직 없다. manifest 에도 `installGuideUrl` 필드가 빠져 있다.
- 런처가 정식 경로가 되면서 자연 흡수된 면이 있지만, 수동 zip 폴백 트러블슈팅(특히 macOS 첫 실행 / Windows SmartScreen) 한 페이지는 유지하는 게 좋다.

### 5) 피드백 폼 실체 연결
- 런처·portal·patch-notes 어디든 `feedbackUrl` 은 `https://rivai-portal.pages.dev/feedback` 으로 가는데, 그 자리에 실제 폼(Google Form / Notion / Discord 채널) 이 아직 연결되지 않은 상태일 가능성.
- F01 의 폼 스키마(Tester Name, Build Version, Build ID, …) 대로 폼 한 번 만들어두고, 샘플 제출 1 건으로 끝점 검증.

### 6) Dedicated 서버 운영 관찰성
- `manifest.server` 는 박아두었지만 서버 상태(Online/Offline)·플레이어 수가 portal·런처에 노출되지 않는다.
- 최소: `/status` endpoint 또는 manifest 옆에 `server-status.json` 을 따로 두고 30~60초 주기 갱신. cron / systemd timer 한 줄로 가능.
- 또한 `systemd` unit 파일과 운영 절차 메모가 repo 에 없다(운영 host 안에만 존재) → `Docs` 또는 `Distribution/` 어디든 한 부 캡처해두는 게 안전.

### 7) macOS 만 universal 빌드, 서버는 x86_64
- L01 의 EC2 c5.2xlarge 가 x86_64. Oracle Always Free ARM 도 검토 대상이었지만 일단 AWS 로 정착.
- 운영 단가는 t2.micro Free Tier 영구 적용 가능한지(트래픽·시간) 점검. AWS Free Plan credit 소진 시점을 미리 알 수 있게 Billing Alert 셋업.

### 8) manifest staleness 가시화
- 런처 / portal 모두 manifest 의 `releasedAt` 만 보여준다. "마지막 빌드가 N일 전" 같은 표현이 있으면 테스터가 빌드 시점 인지가 쉬워진다. portal app.js 한 줄짜리 enhancement.

### 9) End-to-end 자동 검증
- 지금은 사람이 portal → 런처 → Play 흐름을 눈으로 본다. 가벼운 smoke test: GitHub Action 에서 manifest fetch → R2 HEAD → sha256 round-trip 정도만 nightly cron 으로 돌려도 안전망이 생긴다.

### 10) 패치노트 마크다운 자동화
- G01 에서 의도한 "마크다운 → HTML 변환" 은 아직 미도입. 빌드 횟수가 늘면(이미 0.0.1 ~ 0.1.9-dev 로 12 개) `render-patch-notes.sh` 에 변환 단계 추가가 자연스러운 다음 수.

### 11) 새 빌드 알림 / 차등 패치
- M0 범위 밖. M1 진입 시점에 (a) 런처가 새 빌드 감지 시 사용자 알림, (b) 큰 빌드 zip 대신 차등 patch — 둘 중 선택. 차등 패치는 K01 의 multipart 와 별개 인프라(예: courgette / bsdiff) 필요.

### 12) 비밀 키 회전·로테이션 주기
- `CLOUDFLARE_API_TOKEN`, `R2_ACCESS_KEY_ID/SECRET`, `rivai-notary` keychain profile (App-Specific Password) — 회전 주기 메모만이라도 (G01·J01·K01 운영 규칙 합쳐 한 페이지) 두면 추후 사고 대응이 빠르다.
