## 슬라이드 2 · 웹사이트 → 런처 → 게임 (90초)

화면의 **세 윈도우를 차례로 가리키면서** 진행.

### 가리킬 곳 ①: 왼쪽 브라우저 윈도우
> "사용자가 처음 마주치는 건 우리 포털입니다. `rivai-portal.pages.dev` 에 와서 운영체제에 맞는 다운로드 버튼을 누르면 런처 zip 5MB를 받습니다."

### 가리킬 곳 ②: 가운데 런처 윈도우 (진행률 바)
> "런처를 켜면 사용자가 추가로 할 게 없어요. 자동으로 게임을 다운로드하고 패치합니다. 지금 화면에서는 65% 다운로드 중이죠. 다 받으면 Play 버튼이 활성화됩니다."

### 가리킬 곳 ③: 오른쪽 게임 윈도우 (상단 IP, 캐릭터들)
> "Play를 누르면 게임이 시작되면서 **자동으로** AWS 서버에 접속합니다. 상단에 보이는 13.125.11.128 이 우리 서버 주소예요. 이미 들어와 있는 팀원들과 같은 월드에서 만납니다. **Host냐 Join이냐 IP가 뭐냐를 물어보지 않습니다.** Play 한 번이에요."

### 마무리 (하단 캡션)
> "롤 클라이언트와 정확히 같은 패턴입니다. 사용자가 새로 배울 게 없어요."

→ **전환**: "이게 보여드리고 싶은 사용자 경험이고, 그 뒤에서 이걸 가능하게 하는 인프라는 다음 한 장이 전부입니다."

## 슬라이드 3 · 전체 아키텍처 다이어그램 (2분)

### 시작
> "이 한 장이 답입니다. 처음엔 복잡해 보일 수 있지만 큰 구조는 단순해요."

### 위에서 아래로 짚어주기

**① 위쪽 청록 박스 (Developer)**
> "위쪽은 개발자, 즉 제 로컬 Mac입니다. 여기서 게임과 런처를 빌드하고 `release-game.sh` 같은 스크립트로 배포합니다."

**② 왼쪽 주황 영역 (AWS)**
> "왼쪽 박스가 AWS입니다. Seoul 리전 EC2 인스턴스 하나에 게임 서버가 떠있어요. **서버는 여기 한 곳뿐**입니다."

**③ 오른쪽 주황 영역 (Cloudflare)**
> "오른쪽이 Cloudflare인데, 그 안에 셋이 있습니다. 게임 파일 저장소인 **R2**, 사용자가 보는 웹사이트 **Pages**, 내부 위키용 **Workers**. 사용자 측 자산은 전부 Cloudflare로 모았어요."

**④ 아래 보라 박스 (End User)**
> "맨 아래가 사용자입니다."

### 화살표 한 번 훑기
- 개발자 → AWS: `rsync + systemd` ("서버 배포")
- 개발자 → R2: `wrangler / boto3` ("게임 파일 업로드")
- 개발자 → Pages: `wrangler pages deploy` ("포털 배포")
- 사용자 → Pages: 포털 방문
- 사용자 ← R2: 게임 다운로드
- 사용자 ↔ AWS: `UDP 7777` 게임 트래픽 (점선 = 실시간)

→ **전환**: "이제 두 클라우드를 하나씩 들여다보겠습니다. 먼저 AWS."

## 슬라이드 4 · AWS EC2 — 게임 서버 (1분)

### 핵심 비유
> "AWS 측은 단순합니다. **EC2 인스턴스 하나가 게임의 '심판' 역할**을 합니다. 누가 어디 있고 누가 누구를 맞췄는지는 이 서버가 결정해요. 클라이언트는 결과를 받아 화면에 그릴 뿐입니다."

### 세 카드 짚기
**① 위치 — Seoul**
> "한국 팀원과의 거리를 줄이려고 Seoul 리전에 뒀어요. 지연시간(=ping)이 가장 중요해서 그렇습니다."

**② 실행 파일 — RivaiServer**
> "게임 클라이언트가 아니라 화면이 없는 **headless 빌드**입니다. 그래픽 모듈을 통째로 뺀 가벼운 버전이에요."

**③ 상주 방식 — systemd**
> "Linux의 표준 데몬화 방식으로 24시간 떠있게 했습니다. 죽으면 자동 재시작, 서버 재부팅돼도 자동 시작."

### 터미널 박스 짚기 (선택)
> "운영자가 서버에 SSH로 들어가서 상태나 로그를 보는 건 이런 식입니다."

→ **전환**: "AWS는 끝. 다음은 사용자 측 인프라, Cloudflare입니다."

## 슬라이드 5 · Cloudflare 3종 세트 (1분)

### 전체 톤
> "사용자 측은 셋 다 Cloudflare로 통일했습니다. 역할이 셋이에요."

### 카드별로

**① R2 — 파일 저장소**
> "R2는 우리 게임 zip과 manifest가 사는 곳입니다. **R2의 결정적인 장점은 egress 비용이 0이라는 것**. AWS S3는 사용자가 다운로드할 때마다 돈을 내야 하는데, R2는 사용자가 100번 받든 1000번 받든 추가 비용이 없어요. 500MB짜리 게임을 배포하는 입장에서는 게임 체인저입니다."

**② Pages — 웹사이트**
> "Pages는 사용자가 처음 마주치는 정적 웹사이트입니다. 홈, 다운로드, 패치노트, Known Issues, 피드백 — 전부 여기서 제공합니다."

**③ Workers Static — 위키**
> "Workers는 내부 개발 위키용입니다. road-to-rivai 마크다운을 정적 HTML로 빌드해서 호스팅해요. 사용자가 보는 자료가 아니라 우리 팀 문서 전용입니다."

### 마무리
> "셋 다 `wrangler` 라는 CLI 하나로 배포되기 때문에 운영이 단순합니다."

→ **전환**: "지금까지가 정적인 그림이고, 이제 이게 **실제로 어떻게 도는지**를 봅시다."

## 슬라이드 6 · 실제 동작 — manifest 패턴 (2분)

### 시작
> "사용자가 런처를 켤 때부터 게임에 들어갈 때까지의 흐름입니다. **핵심 개념은 manifest 하나**예요."

### 왼쪽 5단계 짚어가며

**① 런처 시작**
> "사용자가 런처 아이콘을 더블클릭합니다."

**② manifest fetch**
> "런처가 가장 먼저 하는 일은 R2에 있는 manifest 파일을 읽는 것입니다."

**③ 버전 비교 + 다운로드**
> "사용자가 가진 버전과 manifest의 latestVersion을 비교해요. 다르면 게임 zip을 다운로드하고, SHA256으로 무결성을 검증한 뒤 압축을 풉니다."

**④ Play 클릭**
> "사용자가 Play를 누르면 런처는 manifest에서 읽은 **서버 주소를 commandline 인자로 게임에 넘기면서** 실행시킵니다."

**⑤ 자동 서버 접속**
> "게임은 시작하자마자 인자를 보고 곧바로 AWS 서버에 connect합니다."

### 오른쪽 JSON 짚기
> "이게 실제 manifest입니다. 보시면 `latestVersion`, 게임 zip의 `downloadUrl`, 그리고 게임 서버 `host`와 `port`가 다 들어있어요."

### 결정적인 한 문장
> "**이 JSON 한 줄을 갱신하는 것 = 모든 사용자의 다음 행동을 바꾸는 것**입니다. 게임을 재빌드할 필요도, 런처를 재배포할 필요도 없어요. 다음 슬라이드에서 이게 실제 업데이트에서 어떻게 작동하는지 보겠습니다."

→ **전환**: "그럼 그 manifest를 어떻게 갱신하느냐 — 명령어 한 줄입니다."

## 슬라이드 7 · 실제 업데이트 — release-game.sh (1.5분)

### 시작 (코드박스 짚기)
> "새 빌드를 푸시하는 건 이 한 줄입니다. 버전, 빌드 ID, 채널, 그리고 클라이언트 zip 경로를 인자로 줍니다."

### 5단계 짚어가기

**① SHA256 + 크기 계산**
> "파일 무결성용 해시와 다운로드 진행률용 크기를 미리 계산합니다."

**② R2 업로드**
> "게임 zip을 R2 버킷에 PUT합니다. 300 MiB가 넘으면 wrangler 단일 PUT 한계 때문에 boto3 멀티파트 업로드로 자동 전환됩니다."

**③ manifest 갱신**
> "조금 전 슬라이드에서 본 그 JSON을 다시 만들어서 R2에 PUT합니다. **이 순간 모든 런처가 다음에 켜질 때 새 버전을 보게 됩니다.**"

**④ 패치노트 렌더**
> "템플릿으로 패치노트 HTML을 만들어 portal 디렉토리에 떨어뜨리고, 인덱스 페이지 맨 위에 새 행을 끼워 넣고, `/latest/` 리다이렉트를 갱신합니다."

**⑤ Pages 재배포**
> "마지막으로 wrangler가 포털 자체를 다시 배포합니다."

### 마무리
> "**멱등(idempotent)**으로 설계되어서, 같은 명령을 두 번 돌려도 안전합니다. 실수로 다시 돌려도 같은 결과만 나옵니다."

→ **전환**: "이게 슬라이드 설명이고, 이제 진짜로 돌려서 보여드리겠습니다."

## 슬라이드 8 · 라이브 데모 (5-7분)

> "지금부터 4단계로 실제 릴리스를 보여드릴게요. 화면을 슬라이드와 터미널, 브라우저로 자주 전환할 테니 따라와 주세요."

### STEP 1 — 현재 상태 (1분)

**터미널**:
```bash
curl -s https://pub-0ac7d3ef69e344e1bb87f0d1475315cb.r2.dev/manifest/dev.json \
  | jq '{latestVersion, releasedAt, server}'
```

> "지금 R2에 떠있는 manifest입니다. `latestVersion`이 0.1.0-dev네요. `server.host`는 우리가 본 그 AWS EC2 IP."

**브라우저 탭 A (포털)**: 같은 버전이 표시되는 것 확인.

---

### STEP 2 — dry-run 시뮬레이션 (2분)

**터미널**:
```bash
./scripts/release-game.sh \
  --version 0.1.99-demo \
  --build-id 2026.05.20.demo \
  --channel dev \
  --client-mac /tmp/rivai-demo.zip \
  --notes /tmp/demo-notes.json \
  --dry-run
```

> "**`--dry-run`** 을 붙이면 어떤 일이 일어날지만 출력하고 실제로는 아무것도 안 바뀝니다. R2에 어떤 키로 올릴지, manifest는 어떻게 갱신될지가 다 보여요."

**가리킬 출력**: `[dry  ]` 접두어 라인들

> "실수 방지용으로 매우 유용합니다 — 새 환경 만지기 전에는 거의 항상 dry-run 먼저 돌립니다."

---

### STEP 3 — 진짜 실행 (3분)

**터미널** (위와 동일하지만 `--dry-run` 제거):
```bash
./scripts/release-game.sh \
  --version 0.1.99-demo \
  --build-id 2026.05.20.demo \
  --channel dev \
  --client-mac /tmp/rivai-demo.zip \
  --notes /tmp/demo-notes.json
```

**출력 짚어가기**:

| 출력 라인 | 한 마디 |
|---|---|
| `mac: 547MB <sha>` | "1단계 — SHA256 계산 끝" |
| `R2 upload: rivai-dist/builds/...` | "2단계 — R2 업로드 (실제 wrangler 호출)" |
| `R2 upload: rivai-dist/manifest/dev.json` | "**3단계 — 이 순간 모든 런처가 새 버전을 보게 됩니다**" |
| `inserted new row` / `updated latest` | "4단계 — 패치노트 인덱스 갱신" |
| `wrangler pages deploy …` | "5단계 — 포털 자체 재배포" |
| `done.` | "끝났습니다. 30초 ~ 1분 걸렸네요." |

---

### STEP 4 — 결과 확인 (1분)

**터미널** (Step 1 명령 재실행):
```bash
curl -s https://pub-0ac7d3ef69e344e1bb87f0d1475315cb.r2.dev/manifest/dev.json \
  | jq .latestVersion
# → "0.1.99-demo"
```

> "보세요, **manifest의 latestVersion이 바뀌었습니다**."

**브라우저 hard refresh** (`Cmd+Shift+R`):
- 탭 A (포털 홈) → 새 버전 표시
- 탭 B (패치노트 인덱스) → 맨 위에 새 행
- 새 탭에서 `rivai-portal.pages.dev/patch-notes/0.1.99-demo/` → 렌더된 노트

> "이제 어떤 사용자가 런처를 켜면 바로 이 새 버전이 보입니다. 슬라이드 6에서 본 manifest 패턴이 이렇게 작동하는 거예요."

---

### (선택) STEP 5 — 런처 자동 픽업

런처 실행 → manifest fetch → 새 버전 알림 → 다운로드 → Play.

> "사용자가 한 일은 런처를 켠 것뿐입니다."

---

### 마무리

> "오늘 정리하면 —
> AWS 한 곳에 게임 서버, Cloudflare에 사용자 측 자산 전부.
> manifest 한 파일이 모든 사용자의 다음 행동을 결정.

## ⚠️ 데모 실패 대비책

| 증상 | 대응 |
|---|---|
| `wrangler` 인증 만료 | 발표 전 `wrangler login` 미리 확인 |
